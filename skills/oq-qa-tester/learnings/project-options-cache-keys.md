**Trigger:** Seeding an option pre-state with SQL (`options` / `options_variants`) and then expecting the application to read it — a scoped/global `default_language_code_frontend`, `foreign_languages_initialized`, any project option.

**Rule:** The live project-options cache keys in KeyDB **db0** are `<projectId>:optionsVariants:preloaded:global`, `<projectId>:optionsVariants:preloaded:<salesChannelId>`, `<projectId>:optionsVariants:ts:global`, `:ts:<salesChannelId>` and `:invalidation:ts`. Do NOT trust `OptionsLoader`'s `<id>:options` / `<id>:options:ts` names (stale code path) and not `KeyValDb::SILO_PROJECT_OPTIONS_DB = 7` either — both matched nothing on the dev stack (2026-09-17). Invalidate with `./docker/dev compose exec -T keydb sh -c 'redis-cli -n 0 --scan --pattern "<id>:optionsVariants:*" | xargs -r redis-cli -n 0 DEL'` and confirm the count it prints is non-zero. A DEL that returns 0 means the app is still reading the OLD values, and every result after it is worthless: writes performed by the app itself invalidate correctly, so a run can look right while a SQL-seeded precondition never took effect. Sanity-check the pre-state through a real request (e.g. an uninitialized-add-on storefront must answer 200 with the `default_language_code`) before drawing conclusions. Related pre-existing bug: `LocalizationFrontend.php:141` tries `del(sprintf('%s:options*', $projectId))` and `Redis::del()` does not glob, so that recovery path invalidates nothing.
