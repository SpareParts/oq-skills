**Trigger:** Admin AJAX/POST requests (fetch from a logged-in tab, form saves) never return while plain page GETs and anonymous `curl` still work; proxy log shows "client prematurely closed connection ... while sending request to upstream"; www log says "[pool www] server reached pm.max_children"; a tab that landed on a heavy Tracy bluescreen freezes (JS/network tools time out) and subsequent `navigate` calls to that host report success but never commit.

**Rule:** The requests are blocked on a file lock, not on the app. Diagnose in this order inside `www`: `for p in $(pgrep -f "pool www"); do cat /proc/$p/wchan; done` (all `locks_lock_inode_wait`), then `cat /proc/<pid>/syscall` → `32 0xe 0x2` = `flock(fd 14, LOCK_EX)`, `readlink /proc/<pid>/fd/14` → `/var/www_logs/php/php_events.log` (Monolog StreamHandler locking), confirm with `timeout 5 flock -n /var/www_logs/php/php_events.log -c 'echo ok'` (BUSY = held). `/proc/locks` in `www` will NOT show the holder (the log lives on the btrfs `/var/www_logs` volume); scan the other containers instead: in `supervisor`, `ls -l /proc/*/fd | grep php_events.log` + `grep lock /proc/<pid>/fdinfo/<fd>` found two `messenger:consume asyncJobs` workers holding `FLOCK WRITE` for 21 h (2026-09-10). `kill -TERM` them (supervisord respawns) and the queue drains within seconds. The Tracy session flock (`/var/lib/php/sessions/tracy-<id>`) shows up first in `/proc/locks` but is a symptom: its holder is itself waiting on the log lock. Killing individual php-fpm children only frees their slot. Requests that write no non-debug log line (most page GETs) pass, which is why the hang looks endpoint-specific. Side fact: the request header `Disable-Tracy-Panel: 1` puts Tracy into production mode for that request (`DebuggerConfigurator::showPanel`), but it does not help here. Freeze the frozen tab out: create a new tab rather than retrying navigation.
