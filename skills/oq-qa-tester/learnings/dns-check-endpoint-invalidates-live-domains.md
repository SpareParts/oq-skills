**Trigger:** QA on multishop DNS validation, the connect-custom-domain wizard, or anything that writes `project_domains.isRoutingValid` (`SaveDnsValidationSnapshotCommand`), from PR #44800 on.

**Rule:** `POST /admin/multishop/connect-custom-domain/dns-records/` and `.../create-market-wizard/dns-records/` take `{domain, setupMethod, validate}` from the request body and write the verdict onto whatever ACTIVE `project_domains` row carries that hostname — no ownership check, no comparison with the row's stored `setupMethod`, no "was valid until now" guard. `validate:1` with a negative verdict sets `isRoutingValid = 0`, the row leaves `routing_domains_active`, and the host stops resolving to the project entirely (storefront answers 302 to `www.shoptet.cz/projectAction/InactiveProjectRouter/`). Two cheap ways to trigger it on a live domain: a host with no DNS (`hehe.cz` on project 704384), or a healthy host checked with the WRONG method (`rofl.myshoptet.com` + `delegated_nameservers` — its stored method is `core_records`). `recomputeCanonical` then promotes the channel's internal alias, so the market stays reachable on `<projectId>-<marketId>.myshoptet.com` while the customer-facing domain is dead. Restore with `UPDATE project_domains SET isRoutingValid=1, isCanonical=1, routingValidatedAt='<snapshot>' WHERE id=<row>` plus `isCanonical=0` on the alias, and delete the `dns_validation_results` rows (two per check: `routing` + `emails`). Checking a healthy domain with its CORRECT method is safe — it only refreshes `routingValidatedAt`. The fleet-wide `dnsValidation` cron (job 5720, `mode=all`, `0 */4 * * *`, projectPreset active) does NOT do this: `DnsValidationRunner` writes only `dns_validation_results` snapshots and never touches routing validity — check that before reporting a mass-outage vector.
