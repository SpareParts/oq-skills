**Trigger:** Attributing a 500 to a request because a fresh `exception--*.md` appeared in `/var/tmp/exceptions/` (container) with a full middleware stack trace.

**Rule:** Those Tracy bluescreen files are ALSO written for exceptions that were caught and merely logged with `'exception' => $e` context (e.g. `DnsRecordsProvider`'s per-record "Skipping invalid DNS record" debug log) — and a caught exception's trace still shows the whole Kernel/Messenger call chain, so the stack cannot distinguish caught from uncaught. Verify the actual HTTP status of the request (response capture, FE state that only a 2xx could produce) before reporting a 500. Concrete case 2026-08-25: two CAA-parse exception files fired during a `connect-custom-domain/dns-records/` call that returned 200. The converse also holds (2026-08-26): the admin "A safra! Něco se pokazilo." error page can render with NO new exception file at all — absence of a Tracy file is not proof the request succeeded either. Both directions: verify the actual HTTP response, never the exceptions directory.
