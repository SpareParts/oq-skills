**Trigger:** Creating a domain redirection through the admin UI (`/admin/dns-presmerovani/?id=<marketId>` Add modal → `POST /admin/dns-redirection/create/`) to exercise the storefront `project_domains` redirect path (`GetDomainRedirectionQuery` → `routing_domains_active`).

**Rule:** Two traps decide the source host. (1) A `*.myshoptet.com` source is rejected as "domain taken": `RedirectionUrlNormalizer::getBaseDomain` keeps the last two labels (`myshoptet.com`) and `RedirectDomainsHelper::isDomainTaken` matches every other project's `projects_active.url` with `LIKE '%myshoptet.com/'` — so the cert-friendly synthetic hosts from synthetic-hosts-myshoptet-wildcard-cert cannot be created via the UI (SQL seeding still works). (2) A `www.` source never hits the NEW path: the UI stores `https://www.<host>/` (view: `www.<host>`) while `GetDomainRedirectionQueryHandler` runs the request host through `DomainNormalizer`, which strips `www.` — the storefront still 301s because the Create service also writes the legacy `domain_redirects` row, and the `env:<host>` blob then carries `redirect_url` only (no `project_domain_redirect_url`). To prove the new path from the UI use a BARE foreign host such as `qa<ticket>-redir.cz` (accepted by `HostnameValidator`), check the blob for `project_domain_redirect_url`, and drive the storefront with `curl -sk` (the dev cert is `*.myshoptet.com.test`, so Chrome shows an interstitial for that host). The write-side invalidation (`ProjectDomainWriteRepository::clearRoutingCache` via `ProjectDomainHostnameNormalizer`) does keep `www.`, so `env:www.<host>` is dropped correctly on update/delete (verified 2026-09-08, PR #43919).
