**Trigger:** A scenario needs a race between two admin requests (e.g. to hit a `SELECT … FOR UPDATE` write-path guard behind a validator that screens the same condition first) and you fire them concurrently via `Promise.all` from one logged-in tab.

**Rule:** The PHP session lock serializes same-session admin requests — the "loser" runs entirely after the winner commits and fails at the earlier validation layer, never reaching the write guard. A single browser profile cannot hold two admin sessions (one cookie jar), so the guard branch is effectively unreachable from browser QA. Assert the INVARIANT instead (one 201 + one 4xx, exactly one row after a concurrent double-submit) and lean on the PR's unit/integration tests for the guard branch itself; report that explicitly rather than claiming the guard was exercised.
