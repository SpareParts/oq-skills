**Trigger:** A PR adds a DB-backed lookup (QueryBus handler, repository, `CmsDatabase::getConnection()`) into `ProjectConstants::getEnvironment()` / `defineConstants()` / `EnvironmentSetupMiddleware` that runs BEFORE `ProjectConstants::loadEnvironment()` — typically to fire a redirect or exit "ahead of the legacy exit paths".

**Rule:** `CmsDbDriver` is configured only inside `loadEnvironment()` (`$this->database->configureDriver(CmsDbDriver::class, …)`); `DatabaseConnectionMiddleware` runs *after* `EnvironmentSetupMiddleware`. Anything that touches the CMS DB earlier throws `LogicException: Database driver "CmsDbDriver" is not configured.` (`lib-common/src/Database/DbDriver.php:162`). When the caller wraps it in `catch (Throwable)` the failure is silent at HTTP level: the new branch never fires, the request falls through to the legacy path (unknown host → 302 `InactiveProjectRouter`), and EVERY storefront request — homepage, images under `/user/shop/detail/*`, everything — writes one ERROR line. Unit/integration tests do not catch it because the test bootstrap configures the driver up front (verified 2026-09-07, PR #43919 head 74d94ef). Verify with a cold storefront request on a seeded host + `php_events_json.log` (see php-events-json-log-proves-caught-exceptions); a 302 to InactiveProjectRouter where a 301 was expected is the tell.

**2026-09-08 update:** PR #43919 head `176242aa987` resolved this by moving the lookup INTO `loadFreshEnvironment()` (after `resolveFreshEnvironment()` configured the driver) and attaching the result as data (`project_domain_redirect_url`) on the cached blob, with the `isFrontOffice()` gate applied at read time in `getEnvironment()`. Verified: cold storefront 301 on seeded hosts, error counts in `php_events_json.log` unchanged across ~30 requests. The rule still applies to any other pre-`loadEnvironment()` DB access.
