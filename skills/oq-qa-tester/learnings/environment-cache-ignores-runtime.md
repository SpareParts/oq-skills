**Trigger:** QA'ing any new branch inside `ProjectConstants::loadFreshEnvironment()`/`getEnvironment()` that is gated on `Environment::isFrontOffice()` (or any other runtime check) to keep it storefront-only (or admin-only) — e.g. a new redirect, an experiment, a maintenance mode.

**Rule:** `ProjectConstants::loadEnvironment()` caches its whole resolved result in Redis under `env:<domain>` — keyed **purely by domain, with no runtime dimension**. The runtime gate inside `loadFreshEnvironment()` only runs on a cache MISS; a cache HIT skips it entirely and just replays whatever was cached, regardless of which runtime asks. Concrete case (2026-09-03, PR #43919/CZ3MUL1-974): a new `Environment::isFrontOffice()`-gated multishop redirect was correctly skipped on a cold admin request (control), but once a storefront hit for the same domain populated `env:<domain>` with `{"redirect_url":...}`, a subsequent ADMIN request for that domain got 301-redirected too — the gate never got a chance to run. The failure is symmetric: an admin-first "unknown project" resolution (cached ~2h, explicit `expires_at`) can just as easily suppress a legitimate storefront redirect for real visitors. Also note the TTL asymmetry: branches that set `expires_at` (e.g. the "unknown" path) cache for ~2h; branches that don't (e.g. this new redirect branch) fall through to a much longer default (~30 days, observed 2,591,705s) — check `redis-cli TTL "env:<domain>"` to see what you're dealing with. **To test a runtime-gated branch here properly:** always probe BOTH orders on a domain never seen by either runtime — (bare/cold) admin-first as a control, then a fresh, never-touched domain for the storefront-first/admin-second regression check — and inspect `redis-cli GET/TTL "env:<domain>"` directly rather than trusting one request's outcome. Clean up seeded rows AND the `env:<domain>` Redis keys they create (`redis-cli -h keydb DEL "env:<domain>" ...`), not just the DB rows.

**2026-09-07 update:** PR #43919 head `74d94ef` moved the multishop redirect lookup out of `loadEnvironment()` (runs on every `getEnvironment()` call, never cached) — the concrete leak above no longer reproduces on that head, but the relocation introduced the unconfigured-driver failure described in db-lookup-before-loadenvironment-unconfigured-driver. The rule itself still applies to any other branch inside `loadFreshEnvironment()`.

**2026-09-08 update:** The shape that finally held (PR #43919 head `176242aa987`): cache runtime-AGNOSTIC data on the blob (`project_domain_redirect_url` next to `unknown`/`redirect_url`) and gate on the runtime only when READING it. Verified in both orders on fresh hosts — admin-first writes the blob with the key and still 302s, the following storefront hit 301s from that cached blob; storefront-first then admin → 301 then 302. When QA'ing a fix of this class, assert the blob CONTENT (GET) is identical regardless of which runtime warmed it, not just the HTTP outcomes.
