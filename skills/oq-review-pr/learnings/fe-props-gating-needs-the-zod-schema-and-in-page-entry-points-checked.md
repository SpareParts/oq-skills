# A frontend props-gating PR needs the page's zod schema checked for the new prop, and the gated pages swept for in-page entry points (buttons, modals, tabs), not only navigation links

Why: the page's props contract lives in the zod schema handed to the page factory, `page(Schema, Component)`, and that wrapper validates with `schema.parse` only to report failures — it neither throws nor hands parsed output to the component, which keeps rendering from the raw payload. Two failure modes follow, and neither turns a test red. First, a plain `z.object` strips unknown keys: a schema that omits the new gating key validates green — tsc would flag the missing contract, but the test fixtures' `as PageProps` cast is what silences it — and the page keeps reading whatever the payload carries. Second, even when the key is declared, a payload that does not carry it (e.g. the frontend ships before the backend, normal for a stacked pair) makes the prop `undefined`; the schema rejects it, the wrapper records a zod report, and rendering continues anyway — the gate never engages and the page silently renders as non-trial. The page tests do not catch either mode: their fixtures hand-build the props object (cast `as PageProps`) and pass it straight to the component, so the schema parse runs but is never the thing under test and an absent key produces no red test — "the fixtures carry the prop" proves nothing about runtime wiring. Separately, proving "every navigation link into the blocked flow is hidden" has not proven the flow unreachable: the same page can own controls that reach it without a link — a button that opens a modal, a tab, a preset picker that routes onward — and those survive a link-only sweep. Check three things: (1) every union member of the page's zod schema carries the new key (a key added to one variant and not the others leaves that variant's pages un-gated); (2) the page component actually reads the prop the schema now declares; (3) inside each touched page, list the buttons/modals/tabs that lead into the gated flow and either gate each one or say why it is unreachable.

Evidence: shoptet/cms4#47037 review (task MIN-128, 2026-10-27). The internal review knew the schema mechanism — its finding 3 stated that `validate()` in `Core/utils/page.tsx` reports rather than throws, so a stacked FE shipping before its BE renders `isTrial` `undefined` and ungated — and its reachability sweep covered links, disabled buttons, form inputs, tabs, the wizard Stepper, store persistence and direct URLs. What it still missed, and the human reviewer's comments then caught: comments 4387150527 and 4387888820 found one in-page chain the sweep's framing did not treat as an entry point (`DnsSettingsGeneralDns` change-dns-management button → `DnsManagementMethodModal` → `DomainSetupPreset`, ungated; closed at the backend in commit 33d0fea710), and comment 4387733987 on #47036 raised the hand-maintained schema question the review never made explicit: the schema did carry `isTrial: z.boolean()` in all three union members (`MultishopDnsSettings/schema.ts:53/73/84`), yet nothing would have caught its absence, because the page fixtures are never parsed by the schema under test. Same family as `msw-override-a-test-never-awaits-pins-nothing` (a test that never exercises the parsing path pins nothing): there the poll was never awaited, here the schema is never the thing under test.
