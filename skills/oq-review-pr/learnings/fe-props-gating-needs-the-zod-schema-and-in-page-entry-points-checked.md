# A frontend props-gating PR needs the page's zod schema checked for the new prop, and the gated pages swept for in-page entry points (buttons, modals, tabs), not only navigation links

Why: the page's props contract lives in the zod schema handed to the page factory, `page(Schema, Component)`, and that wrapper validates with `schema.parse` only to report failures — it neither throws nor hands parsed output to the component, which keeps rendering from the raw payload. Two failure modes follow, and neither turns a test red. First, a plain `z.object` strips unknown keys: a schema that omits the new gating key validates green, nothing in the stack notices the contract is missing the key, and the page keeps reading whatever the payload carries. Second, even when the key is declared, a payload that does not carry it (e.g. the frontend ships before the backend, normal for a stacked pair) makes the prop `undefined`; the schema rejects it, the wrapper records a zod report, and rendering continues anyway — the gate never engages and the page silently renders as non-trial. The page tests do not catch either mode: their fixtures hand-build the props object (cast `as PageProps`) and pass it straight to the component, so the schema parse is never the thing under test and an absent key produces no red test — "the fixtures carry the prop" proves nothing about runtime wiring. Separately, proving "every navigation link into the blocked flow is hidden" has not proven the flow unreachable: the same page can own controls that reach it without a link — a button that opens a modal, a tab, a preset picker that routes onward — and those survive a link-only sweep. Check three things: (1) every union member of the page's zod schema carries the new key (a key added to one variant and not the others leaves that variant's pages un-gated); (2) the page component actually reads the prop the schema now declares; (3) inside each touched page, list the buttons/modals/tabs that lead into the gated flow and either gate each one or say why it is unreachable.

Evidence: shoptet/cms4#47037 review (task MIN-128, 2026-10-27). The internal review (artifact a946c77a) approved with "All UI entry points to this page are gone for trials", but the human reviewer's comments 4387150527 (`DnsSettingsGeneralDns` change-dns-management button → `DnsManagementMethodModal` → `DomainSetupPreset`, ungated) and 4387888820 (same hole, later closed at the backend in commit 33d0fea710) found the in-page entry point the link-only sweep missed. The schema question raised on #47036 (comment 4387733987) the internal review never mentioned: the schema did carry `isTrial: z.boolean()` in all three union members (`MultishopDnsSettings/schema.ts:53/73/84`), but no test would have caught its absence, because the page fixtures bypass the parse. Same family as `msw-override-a-test-never-awaits-pins-nothing` (a test that never exercises the parsing path pins nothing): there the poll was never awaited, here the schema is never the thing under test.
